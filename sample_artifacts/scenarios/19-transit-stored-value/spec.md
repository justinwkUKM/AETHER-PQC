# TransitVault Stored Value Architecture And Security Specification

Fictional product: **TransitVault Stored Value**
Deployment model: **hybrid transit payments**
Scenario purpose: stored-value transit and mobility card platform

## 1. Executive Summary
This document registers the cryptographic controls and systems design of Stored Value Transit and Stored Value Mobility Card, the region's multipurpose contactless stored-value card platform. Stored Value Transit cards are used across the region's public transport network (MRT trains, transit buses), retail merchants, and Electronic Toll Pricing (ETP) motoring toll systems.

Contactless card architectures operate in micro-second windows under strict processing limits. They rely on symmetric card keys (DESFire/Mifare 3DES/AES-128 keys) to deduct funds directly from local hardware chips. The clearing files generated by transit gates and ETP gantries are batch uploaded via SFTP, where the primary risk is long-term key compromise and historic batch modification.

## 2. Infrastructure Inventory & Exposure Model

The system boundaries are defined by five high-volume transaction entities:

### Node 1: Transit Gate Ingest Terminal
* **Label**: `Application`
* **Vulnerability Score**: `6.8` (Constrained Edge Edge)
* **Cryptographic Primitives**: 
  * Current: `Contactless chip communication utilizing Mifare/DESFire legacy 3DES keys, batch transfers via SFTP secured with static RSA-2048 keys`
  * Target Migration: `SFTP channels upgraded to hybrid post-quantum SSH leveraging ML-DSA-65 keys`
* **Purpose**: Contactless reader at transit gates, ETP gantries, and car parks that reads contactless smartcards and registers batch records.

### Node 2: Stored Value Validator
* **Label**: `SoftwareComponent`
* **Vulnerability Score**: `8.0` (Core Balance Verifier)
* **Cryptographic Primitives**:
  * Current: `3DES and AES-128 MAC signature verification for card presentment authenticity`
  * Target Migration: `SLH-DSA or hybrid post-quantum MAC signatures`
* **Purpose**: Verifies card signatures, checks security counters, and validates transaction files to prevent balance duplication and stored-value forgery.

### Node 3: Stored Value Transit HSM Key Store
* **Label**: `DataAsset`
* **Vulnerability Score**: `9.0` (Critical Cryptographic Vault)
* **Cryptographic Primitives**:
  * Current: `Card master keys stored in legacy HSM units wrapped via classical RSA-2048`
  * Target Migration: `Modern post-quantum HSM units with key wrapping protected via ML-KEM-1024`
* **Purpose**: Critical Hardware Security Module (HSM) storing master derivation keys for all Stored Value Transit cards in circulation. High threat of harvesting.

### Node 4: Transit Transaction Ledger
* **Label**: `DataAsset`
* **Vulnerability Score**: `7.5` (High-Volume Archive)
* **Cryptographic Primitives**:
  * Current: `AES-256 database column encryption, with key transport wrapped via classical RSA-2048`
  * Target Migration: `ML-KEM-1024 database envelope wrapping`
* **Purpose**: Database repository recording transit transactions, card serial numbers, and merchant clearing IDs.

### Node 5: Transit Transport Authority (TTA) Host
* **Label**: `ExternalService`
* **Vulnerability Score**: `6.5` (External Sovereign Entity)
* **Cryptographic Primitives**:
  * Current: `Extranet clearing channels secured via standard TLS 1.2 with RSA-4096 certificates`
  * Target Migration: `Strict TLS 1.3 tunnels with hybrid ML-KEM ciphers`
* **Purpose**: Connects the Clearing Services Operator settlement engine to the Transit Transport Authority (TTA) for daily transit clearing and fare distribution.

## 3. Communication Link Relationships

1. **Transit Gate Ingest Terminal** (Application) connects to **Stored Value Validator** (SoftwareComponent) via `DEPENDS_ON` link to upload transaction batches.
2. **Stored Value Validator** (SoftwareComponent) connects to **Stored Value Transit HSM Key Store** (DataAsset) via `PROCESSES` connection to verify card keys.
3. **Stored Value Validator** (SoftwareComponent) connects to **Transit Transaction Ledger** (DataAsset) via `PROCESSES` connection to write audit rows.
4. **Stored Value Validator** (SoftwareComponent) connects to **Transit Transport Authority (TTA) Host** (ExternalService) via `CALLS` connection to settle fares.
